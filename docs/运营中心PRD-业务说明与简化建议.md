# 运营中心 PRD：业务说明与简化建议

版本：V0.1（评审稿）  
日期：2026-09-17  
依据：当前原型页面代码、后端业务逻辑、原始需求及首批实施说明。  
文档目的：先理解运营中心做什么，再评审是否按建议简化。本文不代表已调整原型，也不替代原始需求基线。

## 1. 产品定位：把各单位的数据整理成可使用、可追溯、有人维护的资产

运营中心负责回答五个问题：**数据从哪里来、是否合格、存在哪里、如何提供使用、出问题由谁处理。**

例如，自治区需要汇总各市的某类地块数据。运营人员下发报送任务，市级人员提交数据；平台检查缺失字段、重复编号、异常面积等问题，退给责任人修正。合格数据入库后，登记所属目录与责任单位，并按需要发布查询接口。后续发现质量或服务异常，再形成待办交给负责人处理。

运营中心的主要产出是：一份来源明确、质量结论可查、存储位置明确的资产，以及它的报送、整改、发布和维护记录。

“运营”在这里指数据治理和服务运行维护。访问量、用户增长、内容推广等门户运营工作已有其他模块承接。

## 2. 谁使用，分别做什么

| 用户 | 核心诉求 | 日常动作 | 当前实现情况 |
| --- | --- | --- | --- |
| 数据运营管理员 | 知道数据收齐没有、哪里卡住、能否入库使用 | 下发任务、审核材料、组织质检、安排整改、入库、编目和发布 | 由“平台管理员”演示身份集中办理 |
| 数源单位报送人 | 知道自己要交什么、哪里要改、处理到哪一步 | 查看本人待办、保存报送材料、提交、修改后重提、整改反馈 | 已支持本人受派工单与本人整改办理 |
| 数据与服务维护人员 | 确定数据结构、维护接口、处理异常 | 标准与规则配置、建表、服务发布、巡检与告警处置 | 当前仍由平台管理员办理，独立岗位权限尚未落地 |

建议首轮简化先围绕“管理员”和“报送人”设计，专业配置按职责展开。按单位、区划划分的细粒度岗位权限需后续明确，不能将当前演示权限当作正式授权方案。

## 3. 与其他中心的边界

| 用户的问题 | 主要负责模块 | 运营中心提供什么 |
| --- | --- | --- |
| 这份数据来自哪里、合不合格、由谁维护？ | 运营中心 | 来源、质量记录、技术目录、责任单位、运行状态 |
| 谁能看到、谁能申请、怎样授权和交付？ | 资源中心 | 提供同一资产的引用；共享策略、申请和授权仍在那里办理 |
| 数据的业务含义是什么，AI 如何理解？ | 智能中心 | 关联同一资产的元数据和标识，跳转语义标注与引用关系 |
| 有哪些可复用分析工具？ | 工具中心 | 选择相关工具能力，不重复维护一套工具市场 |
| 我今天有哪些跨系统待办？ | 综合集成工作台 | 将报送、审核、整改等任务汇入个人待办 |
| 主机与请求情况如何，详细日志在哪里？ | 统一监控与日志 | 汇总本地业务异常并关联专业监控入口 |

必须保持：技术编目不等于共享授权；发布接口不等于所有人都能访问；解除编目不删除资产。

## 4. 三个核心使用场景

### 4.1 收好一批新数据

前置条件：管理员准备已发布的数据标准、质检规则或模型；入库前准备符合标准的目标空表。

1. 管理员明确报送内容、报送人员、截止时间和采用标准，下发归集任务。
2. 系统为每名报送人生成独立工单；报送人提交 CSV 数据。
3. 管理员审核材料，通过后形成待质检批次；不合适的材料退回重提。
4. 管理员执行质检，系统生成问题清单和质量结论。
5. 有问题时派发整改；责任人提交修正数据，管理员复检，合格后办结整改。
6. 管理员选择目标表并确认字段对应关系，执行入库。
7. 对入库形成的资产登记目录、责任单位和标签；需要提供查询能力时发布接口。
8. 需要对其他用户共享时，继续到资源中心配置共享策略和授权。

**完成判断：**入库成功、资产可定位、采用数据与标准版本可追溯。编目、技术发布和共享状态分别显示，不能用一个“已完成”包办全部含义。

当前注意事项：原型中的归集任务“已完成”仅表示各报送工单审核通过，不能理解为数据已经入库或发布。

### 4.2 管清已有资产

适用于已有库表、资源或已有地图服务，避免为了纳管再重新报送一次。

1. 选择已有资产；需要补充时登记数源或服务地址。
2. 确认名称、来源、责任单位、所属目录和标签。
3. 查看资产相关标准、质量记录、库表、服务和跨中心引用。
4. 按需要进入资源中心共享管理，或登记服务并关联后续维护记录。

**完成判断：**资产已挂接技术目录、责任人或责任单位可追溯，始终引用同一资产标识。

当前限制：外部数据库与 GIS 服务主要支持登记配置，尚不能自动采集元数据或证明远端服务正常。已有外部服务不要求重新发布。

### 4.3 处理运行异常

1. 管理员执行本地业务巡检，检查质检异常、交付失败和服务依赖异常。
2. 系统按规则生成告警，相同规则下同一对象的未关闭告警去重计次。
3. 处置人确认告警，定位来源记录并修复问题，填写处理说明。
4. 再次巡检确认异常恢复；验证通过后人工关闭告警。

**完成判断：**异常已恢复且关闭验证通过，保留原因、处置说明、处理人和时间记录。

当前限制：不是远程服务健康探测，也尚未实现定时巡检、短信或钉钉通知。指标恢复不会自动代替人工关闭。

## 5. 当前原型到底有哪些功能

当前菜单共有 **8 个分组、29 个页面或工作视图**：其中 7 个业务分组，另有运营工作台。原规格中的 43 个页面是目标清单，不是全部已实现功能。

| 分组 | 当前页面数 | 用普通业务语言理解 | 当前可用能力与边界 |
| --- | ---: | --- | --- |
| 运营工作台 | 2 | 看今天要办什么、哪里有异常 | 总览、本人待办；尚无完整多维经营分析 |
| 数据归集 | 5 | 收数据、审材料、入库 | 多人任务、报送、退回重提、字段映射入库；主要为本地 CSV |
| 数据质检 | 5 | 检查数据、派人修正、复查 | 规则模型、手动质检、问题报告、整改复检；不支持在库周期质检和外部模型调度 |
| 数据编目 | 5 | 登记数据来源，把资产分门别类 | 来源系统、数源、技术目录、资产编目和关系；外部元数据自动采集尚未接入 |
| 数据标准 | 2 | 统一数据应该有哪些字段、怎样填 | 标准字段定义、发布版本及变更记录；不含完整命名规范、字典和元模型管理 |
| 数据建库 | 2 | 确定数据放哪里、准备表结构 | 数仓节点、本地按标准建空表；不执行真实外部数据库建表 |
| 数据发布 | 2 | 提供本地查询，登记已有地图服务 | 本地接口发布、试查询、停用；外部图层仅登记待联调 |
| 运行监控 | 6 | 发现异常、安排处理、确认恢复 | 本地统计、日志入口、巡检、规则和告警；远端探测及通知通道尚未接入 |

## 6. 为什么现在显得复杂

以下为页面结构与交互实现分析，尚未通过用户访谈或可用性测试验证。

| 问题 | 当前表现 | 对使用者的影响 | 简化方向 |
| --- | --- | --- | --- |
| 一项工作散落在多个菜单 | 任务、工单、审核、质检任务、报告、整改、入库各有入口 | 用户需要自己记住对象关系和下一步去哪里 | 围绕同一报送数据展示全过程和下一步操作 |
| 概览重复 | 运营总览、归集概览、运行总览共用多组统计内容 | 不清楚哪个首页最适合日常工作 | 默认只保留一个运营工作台，专题统计进入对应模块 |
| 同一记录重复展示 | 归集工单与登记审核都展示工单；质检结果与质量报告分别展示明细和汇总 | 容易误认为需要重复建记录或重复操作 | 按待办视图、状态筛选及统计标签组织 |
| 日常办理与低频配置并列 | 报送审核与模型、规则、标准、数仓节点同时出现在导航中 | 第一次使用要理解大量专业术语 | 日常操作在前，配置集中到管理入口 |
| 技术配置直接暴露 | 字段映射、标准字段需要填写 JSON，版本与编号密集展示 | 普通运营人员难以理解和正确填写 | 使用字段表格和下拉选择，高级信息按需展开 |
| 新流程和历史批次入口并存 | 入库列表下面还有批次表和旧操作入口 | 不确定应走哪条路径 | 统一任务详情入口，历史批次明确标记来源 |
| “通过”“完成”含义不同 | 审核通过、质检执行完成、质量通过、入库成功分别存在 | 容易以为审核完就能提供使用 | 明确展示各阶段状态和阻塞原因 |

这些对象在后台有保留必要，但不必全部成为用户每天切换的菜单。

## 7. 建议的简化版产品结构

以下均为**待评审建议**。建议管理员日常只面对 5 个入口；报送人默认进入自己的待办，不展示全部管理配置。

| 建议入口 | 用户进来要完成的事 | 收拢的现有能力 |
| --- | --- | --- |
| 工作台 | 看我该办什么，立即进入办理 | 运营总览、我的待办、关键异常摘要 |
| 数据归集 | 跟踪一项报送，从材料审核一直办到入库 | 任务、工单、登记审核、批次质检、整改、入库执行 |
| 数据资产 | 找到一份数据，知道来源、质量和提供方式 | 数源关联、资产编目、目录浏览、资产关系、库表与服务详情 |
| 运行监控 | 看有什么异常、谁在处理、是否恢复 | 巡检记录、告警处置、归集状态与服务观测、日志跳转 |
| 配置管理 | 配一次规则，以后办理时直接选择 | 标准、规则模型、来源系统与数源配置、目录维护、数仓节点、告警规则 |

这是收拢入口，不是承诺把 29 个视图强行改成 5 张大页面。专业详情、执行记录和配置页仍可存在，通过业务对象进入。

### 7.1 工作台只回答“今天先处理什么”

默认突出四类事项：待审核报送、待整改或待复核、入库失败、未关闭告警。显示对象名称、当前环节、责任人、截止时间和办理入口。

“新建归集任务”“查看数据资产”作为常用动作；完整历史统计放到次级区域。无数据时解释当前没有任务或尚未执行，不填充模拟成功指标。

### 7.2 数据归集围绕任务和报送记录办理

任务列表先显示：任务名称、报送人数及完成份数、截止时间、当前阻塞、下一步。

任务详情展示各报送人的独立记录；点击某份报送记录，在同一详情中查看以下业务阶段：

**材料报送 → 登记审核 → 质检与整改 → 入库**

- 当前阶段突出一个主要办理动作，例如“审核材料”“执行质检”“复检”“确认入库”。
- 自动带入已关联的报送记录、批次、标准和质检报告；用户不反复搜索相同对象。
- 质检失败时直接展示问题行、字段、原因和整改入口。
- 入库字段映射使用“目标字段—来源字段”表格，支持同名预填与人工确认。
- 目标表不足时提供按标准建表入口；确认结果后返回当前记录继续办理。
- 每次提交、质检和入库仍保留独立记录；版本、快照和内部编号放入“历史与技术信息”。
- 入库后提供“查看资产”“完善编目”“按需发布接口”，不强制每项归集都发布服务。

历史批次也可作为来源进入该办理视图，不强制补造原先不存在的报送任务。

### 7.3 数据资产围绕“一份数据”组织

列表优先显示资产名称、类型、来源单位、技术目录、质量情况和服务状态，支持按名称、类型、目录及状态筛选。

资产详情建议分成四块：

1. 基本信息：来源、责任单位、目录、标签、数据预览。
2. 质量与更新：关联标准、最近质检结论、整改记录、入库记录。
3. 服务与共享：已发布接口或已登记服务；共享授权状态和资源中心入口。
4. 关联与历史：上下游对象、操作历史、版本信息、智能中心入口。

已存在的资产可以直接完善编目；尚未接入的外部资产明确显示“未采集”“待联调”，不显示成已验证正常。

### 7.4 运行监控围绕异常处置

默认展示未关闭告警和处理进度；巡检记录、调用台账作为次级视图，规则移到配置管理。

每条告警提供“看原因—去处理—验证关闭”路径，直接定位引发异常的报送、交付或服务对象。处置过程中保持该告警的上下文。

### 7.5 配置管理提供可复用模板

标准和模型采用可视化字段与规则表格。普通办理人员选择已发布模板；复杂技术信息仅向需要维护的人展开。

此处建议改善配置交互，不扩大当前外部连接、SQL 模型或生产数据库能力。

## 8. 首轮改版需求与验收标准

P0 表示建议首轮完成；P1 表示后续体验完善。该优先级只针对原型简化，不改变原始项目要求。

| 编号 | 优先级 | 需求 | 评审通过后的验收标准 |
| --- | --- | --- | --- |
| OP-01 | P0 | 收拢导航 | 管理员默认看到上述 5 个入口；原菜单能力均有去向，旧链接可定位对应对象 |
| OP-02 | P0 | 统一日常待办 | 管理员能从工作台直接审核和处理异常；报送人只能办理本人受派事项 |
| OP-03 | P0 | 连续办理报送数据 | 已具备标准、模型和空表时，从一份报送详情可完成审核、质检、整改复检和入库，无须到无关列表重新找批次 |
| OP-04 | P0 | 清楚显示阶段状态 | 同一条报送能区分审核、质量、入库结果；质检执行完成但不合格时，不显示为可入库 |
| OP-05 | P0 | 表格化字段映射 | 不写 JSON 也能配置映射；漏选、重复映射或类型不合时指出字段及原因；执行前仍校验目标标准 |
| OP-06 | P0 | 资产集中查看 | 从入库记录直达对应资产，能查看来源、质量及服务；编目后资产标识不变，不创建重复资源 |
| OP-07 | P0 | 连续处理告警 | 从告警定位异常源并返回；未恢复的异常不能验证关闭，关闭后可追溯处理记录 |
| OP-08 | P0 | 保持数据和权限约束 | 原任务、执行历史、资产关联和共享授权保留；菜单、按钮和接口权限一致 |
| OP-09 | P1 | 模板与标准编辑优化 | 能用字段表格维护标准，选择规则组合模型；变更后发布新版本，旧记录仍可追溯 |
| OP-10 | P1 | 补充统计与筛选 | 明确时间、单位等统计范围；点击指标进入同口径列表；没有采样数据的指标显示暂无数据 |

建议验收使用三组演示：一次含退回和整改的新数据报送、一份已有资产直接纳管、一次异常恢复后验证关闭。另验证未授权人员访问、规则变更导致旧报告失效、失败入库重试等异常路径。

## 9. 简化后仍须保留的业务规则

1. 一项归集任务对应多份独立报送工单，不能把一人提交当作所有人完成。
2. 登记审核只判定材料是否接收，不代替数据质检。
3. 质检报告绑定数据、规则和标准版本。相关内容变化后须重新校验，不能沿用不匹配的通过结论。
4. 存在未办结整改时不能入库；映射后的数据仍需满足目标标准。
5. 当前映射入库只支持未发布的本地空表，不覆盖已有表数据；失败重试保留每次执行记录。
6. 技术目录、资产和共享授权分别维护；发布接口时仍执行资源版本和使用授权检查。
7. 告警恢复和告警关闭是两件事，关闭前必须验证。
8. 浏览器返回、刷新或进入关联详情后应保留原筛选与当前对象；编辑未保存时给出提醒。
9. 业务失败需显示可理解的原因，并允许在可重试环节修正后继续。页面合并不能吞掉原始执行记录。

## 10. 本轮不扩展的能力

以下属于完整需求的后续能力或尚未接入项，本轮仅做业务梳理与简化建议，不承诺实现：

- 外部数据库/GIS 真实连接、元数据自动采集、外部数据库建表与写入。
- Excel、GDB、MDB 全流程解析，覆盖式或增量式入库。
- 自助归集、自助质检、在库数据周期质检、SQL/第三方模型、定时调度。
- 专业时序监控、远端服务探测、短信/钉钉通知与升级策略。
- 完整多岗位、单位与区划授权；完整标准字典、命名规范和元模型管理。

首轮不提供未经测量的性能指标或生产容量承诺。原型验收以现有本地演示数据为基础；正式部署的响应时间、批量规模、审计留存期限须另行确认。

## 11. 建议评审的三件事

1. **定位是否认可：**运营中心围绕数据接收、治理、资产管理和运行维护展开。
2. **组织方式是否认可：**采用“工作台、数据归集、数据资产、运行监控、配置管理”五个入口，日常以待办和具体数据为主线。
3. **首轮范围是否认可：**优先降低导航与表单复杂度，保留现有业务规则和历史记录；新增外部接入能力另行排期。

建议先按以上方向确认业务理解，再细化页面稿。当前没有修改菜单、页面或业务逻辑。
