# 应用中心与智能中心改进实现文档

版本：V1.0  
日期：2026-09-15  
状态：实现方案，供评审与后续开发使用；本文所列新增能力尚未实施。

## 1. 结论与建设目标

建议在现有 `prototype/` 上扩展为“统一门户 + 应用中心 + 智能中心 + 公共支撑”。保留当前门户视觉、资源申请闭环及智能中心已实现能力，重点新增场景构建、业务审批流程、应用注册审核和公共支撑模块。

目前的主要问题是应用中心缺少对应领域模型与业务流程，现有原型仍以智能中心为主。不能用智能体广场代替应用中心，用资源申请审核代替业务审批平台，也不能把元数据模板管理当作地图应用模板管理。

本方案按三个层次交付：

1. **现有能力复用与组织调整**：门户、资源目录、智能体、知识、指标、语料、记忆、资源申请和版本机制。
2. **新增可运行原型**：场景配置与运行、流程配置与办理、应用审核上下架、组织授权、服务调用与消息投递演示。
3. **正式集成**：真实二三维地图引擎、流程引擎、身份认证、服务网关、消息中间件、大模型及资源中心接口。此层有单独验收条件，不以本地演示成功代替。

本轮仅输出实现文档，不修改应用代码、演示数据库及已整理的两份正文清单。

### 2.4 关键差距及处理

| 问题 | 影响 | 改进 |
| --- | --- | --- |
| 门户品牌和入口只围绕智能中心 | 应用中心没有承载位置 | 升级平台级名称与导航，智能中心成为独立能力专区 |
| 应用中心 7 个模块缺少独立模型 | 无法形成“配置-审核-运行-治理”流程 | 新建场景、流程、应用目录；公共支撑按平台级入口组织 |
| 概念重名：应用、申请、模板、知识库、流程 | 容易误用对象，造成数据互相污染 | 按第 4 节确立唯一标识与归属 |
| 当前“工具与服务”其实是智能服务入口 | 与原附表工具中心概念混淆 | 改为智能中心的服务区，真实工具资源仍归资源目录 |
| 智能中心功能较完整，但真实 AI 等尚未集成 | 只加页面不能提高实际能力 | 保留本地实现，补质量治理、业务上下文及可替换适配层 |
| 所有管理操作主要由平台管理员执行 | 不能体现区划/单位分级管理 | 新增组织、授权范围和业务角色，服务端统一判定 |
| 单文件前端与整库 JSON 保存 | 新增场景和长耗时任务后耦合与锁竞争增大 | 逐步模块化；领域表增量迁移，长任务不占用状态写锁 |

## 3. 目标信息架构与页面改进

### 3.1 前台门户

保留现有自然资源绿色主色、浅色背景、卡片和顶部导航。建议平台品牌使用“自然资源一张图服务门户”，智能中心不再充当整个平台名称。门户指页面组织方式，不自动意味着向公众开放全部资源；当前业务数据按登录用户权限展示。

```text
统一门户
├── 首页：统一搜索、资源入口、推荐应用、智能服务、知识与动态
├── 资源中心：库表 / 图层 / 工具 / 知识资源目录与申请
├── 应用中心：场景应用 / 业务办理 / 已接入系统
├── 智能中心：资源检索助手 / 智能体广场 / 智能服务
├── 知识中心：政策法规 / 技术规范 / 指南 / 业务手册
└── 个人服务：我的应用 / 我的待办 / 我的资源申请 / 消息 / 会话与偏好
```

主导航保持 5 项，避免简单叠加成一排过长菜单。“智能助手”保留右侧快捷按钮；“智能体广场”和五类智能服务收纳到智能中心。应用中心提供业务使用入口，不向普通用户默认展示模板编辑器、网关配置等管理功能。

首页建议调整：

- 保留搜索主视觉，缩短首屏宣传区域，1440×900 视口下能看到搜索和主要业务入口。
- 搜索可选择“全部、资源、应用、知识”，自然语言提问进入助手；结果标明所属类型，避免把业务应用混在数据资源申请清单中。
- 新增推荐应用区：名称、业务领域、适用区划、提供单位、最近更新时间和“进入应用”按钮。仅出现审核通过且当前用户可发现的应用。
- 五类智能服务用面向业务的名称展示，避免将“元数据标注”“语料管理”等管理术语直接作为门户办事入口。
- 个人待办摘要只显示用户自己的数据；门户推荐内容来自后台推荐配置和真实统计，不写死卡片顺序或数量。

```text
平台管理
├── 管理总览
├── 应用中心
│   ├── 场景构建：地图模板 / 场景应用 / 控件与分组
│   ├── 业务流程：业务体系 / 事项模型 / 流程与表单 / 办件台账

│   ├── 智能体管理
│   ├── 数字资源知识与元数据

│   └── 调用与反馈
└── 公共支撑
```

公共支撑的需求仍归属原附表 1.4.3–1.4.6，仅在产品导航上集中管理。后台总览增加应用状态、流程待办和服务异常；不将资产数量当成“需求建设进度”，原“能力建设进度”建议改为“资产维护概况”。

## 4. 对象归属与跨中心边界

| 概念 | 归属与对象 | 复用与隔离规则 |
| --- | --- | --- |
| 业务应用/场景应用 | 应用中心 `appRegistry`、`sceneApps` | 应用目录保存运营信息，场景保存配置；两者通过标识关联 |
| 资源使用申请 | 现有 `applications`；新接口称 `resourceRequests` | 当前字段不直接改名，提供兼容映射；不与应用目录共表 |
| 地图模板 | 新 `sceneTemplates` | 与现有 `templates` 元数据模板彻底分开 |
| 元数据模板 | 现有 `templates` | 继续供资源字段标注使用 |
| 表单/办件文书模板 | 新 `forms`、`businessTemplates` | 不使用地图模板或语料模板表 |
| 数字资源知识库 | 现有资源目录 + 元数据 + 资源索引 | 描述“有什么资源、如何使用”，不重新复制资源实体 |
| 业务知识库 | 现有 `knowledge` | 法规、政策、操作指南共用文档及版本，业务流程按 ID 引用 |
| 智能体 | 现有 `agents` | 算法/问答执行配置归智能中心；应用目录可登记其入口，不能复制一套智能体配置 |
| 业务审批流程 | 新 `workflowDefinitions/Instances/Tasks` | 人工办理、委托、退回与时限；不复用智能体步骤列表作为审批引擎 |
| 用户权限 | 公共身份与授权服务 | 决定可见/可用/可审批；前台、地图、AI、后台都调用同一判定 |
| 用户记忆 | 现有 `memories/sessions` | 只影响偏好与上下文，不能写入或扩大权限 |
| 网关与消息 | 公共支撑 | 一套网关和消息总线同时服务两个中心，不各建一套 |

应用运行时的有效资源范围为：**用户实时授权 ∩ 应用声明依赖 ∩ 当前已发布且可用资产**。应用获准上架不代表访问者自动获得它所依赖的全部数据。

## 5. 应用中心实现设计

### 5.1 “一张图”场景构建平台

#### 5.1.1 模板、应用与发布

地图模板定义可复用的框架与默认配置；场景应用从模板创建，形成独立草稿与版本。复制模板产生新 ID，不共享可变配置。更新模板不能静默修改已有应用；通过显式“采用新版模板”预览差异后更新草稿。

模板列表保留原文新建、复制、编辑、删除、预览五项。未被使用的模板可确认后永久删除；有关联应用的模板先解除引用，避免把应用配置一并删除。此引用约束属于实现建议，不修改原文“删除后不可恢复”的含义。

#### 5.1.2 配置器

采用“左侧资源与目录 / 中间地图预览 / 右侧属性”的全屏工作区，顶部固定保存、校验、预览和提交审核。长表单用页签分组；预览与用户运行页共用同一个渲染器，避免配置看起来生效而实际应用未使用。

| 配置组 | 必备字段与行为 | 校验与效果 |
| --- | --- | --- |
| 框架 | `engineId`、维度、引擎版本、支持坐标系 | 引擎能力来自注册表；切换先给出不兼容配置列表 |
| 底图 | 分类、节点、服务 ID、坐标系、默认底图 | 原文两级树；有且仅有一个默认底图；不同坐标系不得混选 |
| 图层 | 多棵目录树、图层 ID、可见性、顺序；透明度作为体验增强 | 不允许循环；超过 5 级提醒而非禁止；无权图层不加载 |
| 控件 | 控件 ID/版本、布局、适用终端、参数、能力依赖 | 校验必填参数、引擎/终端兼容性和发布状态 |
| 通用 | 名称、说明、缩略图、主题、服务地址、坐标系、初始范围、全景/相机、高亮及绘制样式 | 视图范围与坐标系一致，服务地址采用受控配置，不将任意地址当作可信接口 |

采用引擎适配接口：初始化、底图切换、图层管理、定位、高亮、绘制、销毁。首批原型可先接入本地二维示例地图；三维项可进行参数配置和兼容校验，但在真实三维引擎接入之前，只记“配置流程已实现、三维运行待集成”，不得标记 1.4.1.1 完整达标。

复用 `bak/` 的地图布局和素材前核对来源与坐标系；不整体搬入旧应用，也不假定当前静态服务能直接加载旧依赖。

#### 5.1.3 控件管理

分组支持新增、重命名、删除；有关联控件的分组不可删除。控件包包含清单：编码、名称、版本、图标、功能描述、地图状态、终端、引擎兼容范围、参数结构、入口和权限声明。

原型只运行已实现的内置控件；上传自定义包后支持校验、登记及信息编辑。任意外部 JavaScript 控件的实际执行待建立隔离运行机制，不在主页面直接执行上传脚本。原型上传和注册流程可验收，任意自定义控件运行另列集成验收。

发布控件后，场景引用明确版本。下架前显示影响应用；下架后禁止新增绑定。原型默认对已运行场景也停止加载该控件并给出替代提示，保留其历史配置；重新发布后由场景负责人确认恢复。后续如需“仅禁止新绑定”的停用策略，应作为单独状态设计。

### 5.2 业务审批流程构建平台

#### 5.2.1 三类审批分开

- **资源申请审批**：沿用现有逐资源审批和期限授权，不改变其业务语义。
- **应用上架审批**：审核应用介绍、入口、配置、权限和依赖；通过后可在门户发现。
- **业务事项审批**：按照业务模型和流程版本创建实例，产生人工任务、办理记录和结果。

三者可共用办理时间线、待办卡片、附件与审计组件；数据对象、状态机和业务权限必须分别定义。

#### 5.2.2 业务模型与配置资源

业务体系采用“业务分组 → 业务体系 → 事项模型”。事项模型绑定流程、表单、操作、知识依据、规则、变量/参数/常量、文书模板、时限策略及可选场景应用。

| 资源 | 页面与行为 | 必须影响的业务结果 |
| --- | --- | --- |
| 流程定义 | 顺序节点为首版，表单/办理人/时限配置，新增编辑删除、校验、预览、部署、发布、导入导出 | 发布版本决定新实例实际流转；导入采用有版本的 JSON Schema，未接入引擎时不承诺 BPMN 互通 |
| 表单 | 内部表单按结构配置并实际渲染；外部表单登记可信入口；虚拟表单映射字段 | 必填、类型和提交校验在前后端一致；外部回调另做适配 |
| 操作 | 名称、编码、适用节点、角色、对应命令 | 只绑定允许的动作，不允许配置任意执行脚本 |
| 法规知识 | 从业务知识库选择文档和发布版本 | 办件侧显示相应依据；不重复保存另一份正文 |
| 常用语 | 分组、内容、适用节点 | 办理意见一键引用，插入后可编辑 |
| 上下班与日历 | 工作时段、周工作日、节假日和调休 | 实际参与截止时间计算；保存时校验时段不重叠 |
| 业务模板 | 模板类型、变量、版本 | 生成本地办理文书预览，变量来源可追踪 |
| 签名 | 所有人、签名图片/标识、有效状态 | 只能使用有权签名；原型图片签名不代表 CA 电子签章 |
| 通用/业务规则 | 条件、结果、作用范围、版本、测试样例 | 实际校验表单或产生辅助判定；用受控表达式，不执行任意代码 |
| 变量/参数/常量 | 编码、类型、来源/值、作用范围、版本 | 变量来自办件上下文，参数来自配置，常量在版本内固定；三者可被规则和表单引用 |

业务资源说明中的“向量库”与子项“常量库”冲突，暂按明确子项实现常量库，冲突保留为需求确认项；不将其误并入 AI 向量索引。

#### 5.2.3 实例与任务操作规则

首版选择可解释的顺序人工流程，完成“提交 → 初审 → 复核 → 办结”；支持串行协办/委办，复杂并行网关、子流程等作为后续引擎能力。原文中的实例操作应逐项落到真实状态变化。

| 操作 | 前置条件 | 状态与效果 |
| --- | --- | --- |
| 提交 | 事项已发布，表单合规，发起人有权 | 固定流程/表单/规则版本，创建首节点待办 |
| 办理通过 | 当前任务待办，操作者是授权办理人或有效代理人 | 原子完成任务并创建下一任务；末节点完成则办结 |
| 挂起/恢复 | 有实例管理权限；非终态 | 暂停任务操作；原型默认暂停 SLA 计时，恢复时按暂停时长重算截止时间并记录依据 |
| 协办 | 当前任务可协办，协办人合法 | 新建关联协办任务；主任务保持原办理人，协办完成后主任务才可继续 |
| 委办 | 当前任务允许委办 | 转移处理责任并保留委办链；原办理人不再直接完成该任务 |
| 委托代理 | 代理授权在有效时间和事项范围内 | 代理人代办记录委托人与实际操作者；授权过期立即失效 |
| 回退 | 目标是已办理的合法前序节点 | 取消当前活动任务，新建回退节点任务；历史记录不可改写 |
| 撤回 | 发起人撤回且后续尚未实质办理 | 取消活动任务；已办理后的撤销走受控作废流程，不默默删除 |
| 作废 | 管理权限、非终态、填写原因 | 实例进入终态，关闭活动任务，保留原数据及记录 |

所有状态变更携带修订号和幂等键；重复提交不产生两个任务，过期页面提交返回冲突并提示刷新。已发布流程不原地修改，存量实例继续执行其固定版本。

#### 5.2.4 工作台、台账与统计

首页八项功能分别落到工作概览、我的待办、项目统计、事项统计、监管决策、最新消息、法律法规、帮助文档。台账支持项目/事项、状态、区划、部门、办理人和时间筛选，列表与统计共用相同过滤条件及权限范围。

建议的演示统计口径：

- 办件总量按 `caseId` 去重；任务量按 `taskId` 统计，不能混用。
- 办件完成率 = 已办结实例 / 当前过滤范围内有效实例；作废和撤回单独展示，默认不计入分母。
- 项目数量按 `projectId` 去重；面积必须有单位，缺少面积的记录标记未登记，不能补零后宣称完整统计。
- 按时/超时办结以 `completedAt` 与按工作日历计算的 `dueAt` 比较；时间范围支持本周、本月、上月、近 7/14/30 天，时区默认 Asia/Shanghai。
- 合规状态与办理状态分别保存；AI 建议不直接将事项标记为“合规”或“已审批”。

以上统计口径为实现建议，进入正式业务接入前由业务负责人核定。

### 5.3 统一用户、SSO 与权限

用户组织不沿用仅“调整区域”的演示表格作为完成标准。新增区划、单位、用户、角色、角色范围、授权操作和外部账号关联。自然人与法人注册方式按原文展示；原型使用虚构身份和可切换验证结果，真实实名核验需对接权威服务。

| 角色 | 核心权限 | 范围约束 |
| --- | --- | --- |
| 平台管理员 | 平台配置与全局治理 | 演示可全局；正式环境按管理职责细分 |
| 区划管理员 | 管辖范围内组织和用户维护 | 不得授予超出本人区划/能力的权限 |
| 单位管理员 | 本单位用户和授权维护 | 不得管理其他单位或扩展区划范围 |
| 应用管理员/审核员 | 场景与接入维护 / 上架审核 | 按负责应用和单位限制；发布审核分权为建议 |
| 流程管理员/办理人 | 流程配置 / 当前任务办理 | 按业务体系和分配任务限制 |
| 智能资产管理员 | 资源语义、知识、指标、语料维护 | 按资产类型和管理范围授权 |
| 资源审批人员 | 资源申请办理 | 沿用现有审批职责，逐步补数源单位范围 |
| 业务用户 | 使用已授权应用、资源、个人会话 | 实时身份与资源授权共同决定 |

服务端统一校验操作权限与对象范围，不能只隐藏菜单。部门和区划改动后，重新检查地图加载、AI 召回、SQL/指标、办件、历史引用和消息详情；历史记录保留，但无权内容不再直接回传。

SSO 原型提供独立演示登录会话、两个示例接入应用、MFA 成功/失败流程、同步状态和登录日志。门户与后台切换不能再自动换成另一名管理员；原 `X-Demo-User` 仅保留为测试模式入口。

正式接入建议采用现有统一身份提供方及其协议；若允许 OIDC，可采用授权码 + PKCE。SDK 负责登录跳转、回调、会话失效处理和退出，不把长期凭据保存到浏览器。AppKey 可展示，AppSecret 仅服务端保管，创建时一次性展示并支持轮换。

对不支持 SSO 的外部系统，原型保存“账号绑定状态 + 凭据引用 + 适配器状态”，用本地受控示例说明 RPA 登录路径；真实密码托管与 RPA 执行列入正式集成，不能用一个跳转按钮宣称已实现。

### 5.4 统一服务网关与消息总线

#### 网关

新增路由、上游实例、调用方、权限策略、限流、超时和调用记录。先用本地两个示例上游验证轮询/故障切换、拒绝无权调用、超限和超时处理，记录 `traceId`、耗时、状态码、调用方及业务对象。

HTTP 服务端与浏览器中的接口调用记录不等同于统一网关。DDoS 防护、WAF、生产负载均衡和高并发稳定性需在实际部署链路验收，不以演示开关代替。

#### 消息总线

事件模型至少有 `eventId`、`eventType`、`aggregateId`、`aggregateVersion`、`occurredAt`、`traceId`。建议事件：`app.listed`、`app.delisted`、`workflow.task.created`、`workflow.case.completed`、`resource.request.decided`、`identity.scope.changed`。

- 事件管理：源注册、过滤、规范化、优先级；原文“清晰”疑似“清洗”，配置名称可使用“规范化”，原编号和疑点保留。
- 订阅管理：事件类型、接收人/系统、筛选、有效期、订阅权限、冲突处理。相同事件对同一订阅只创建一个有效投递单。
- 消息推送：站内消息先落地；Webhook 采用本地示例接收端，记录请求结果。真实邮件、短信等按接入范围扩展。
- 通道管理：实例、启停、队列长度、成功/失败率；原型验证处理器并发配置，生产弹性扩缩容另行验收。
- 可靠性：业务提交与 outbox 事件同事务；异步消费采用至少一次投递，接收端按 `eventId + subscriptionId` 去重。失败按退避重试，达到上限进入失败队列，可人工重试。

身份权限撤销后，已排队消息投递及消息详情打开都需重新鉴权；旧消息保留标题和处理状态，敏感正文与附件按当前权限读取。

### 5.5 应用注册、审核、上下架

统一目录支持 `scene`、`workflow`、`external`、`agent` 类型。智能体类型只引用现有智能体及发布版本，知识或模型配置仍在智能中心维护。统一目录属于组织改进，不扩写原附表中的智能体功能数量。

注册字段：名称、应用类型、责任单位、负责人、说明、图标/截图、业务分类、终端、入口、适用区划、访问策略、所需服务及资源依赖。

```text
草稿 → 待审核 → 已上架 → 已下架
          └→ 已驳回 → 修改草稿 → 再次提交
```

审核通过时发布审核快照，门户只读取该快照。审核后的草稿编辑不影响线上版本；新版本再次提交审核。停用后禁止新进入和新能力调用，历史办件、会话及版本仍保留；打开旧链接显示停用原因或无权限，不跳到空白首页。

## 6. 智能中心改进设计

### 6.1 保留已有成果，补跨中心联动

已有元数据模板和字典联动、批量知识处理、指标计算、图谱、语料评测、SQL/API 试运行、任务接续及对话内申请继续复用。改进重点如下。

| 模块 | 当前基础 | 本轮原型改进 | 正式能力边界 |
| --- | --- | --- | --- |
| 数字资源知识库 | `resources`、字段/字典语义和资源关系 | 增加资源级元数据质量检查、来源完整性、坐标系/更新频次校验、索引状态和失败原因；不要把知识文档去重当作资源清洗已完成 | 真实数据源同步、语义嵌入、索引服务 |
| 资源检索与提示词 | 规则识别、字符特征召回、规则回答模板、发布版评测 | 搜索结果展示命中依据、资源类别和可用状态；提示词工程建立“资源检索”预设筛选，统一到语料库维护 | 提示词正文经模型实际推理、混合召回和重排 |
| 元数据工具 | 字段表格、模板、字典、结构化关系 | 把逗号/竖线文本配置逐步改为字段行、关系选择器；增加未填解释、无效绑定检查和变更影响提示 | 自动标注建议采用模型时保留人工确认 |
| 指标知识 | 本地表数据、复合指标、区域与年度对比 | 业务侧提供结果表/图、口径、来源版本、可比性提示；支持携带区划和场景上下文进入地图 | 真实库表执行、指标服务、业务口径审核 |
| 业务知识库 | TXT/MD 批次、清洗、切片、本地索引、人工图谱 | 分开“处理状态”和“发布状态”；补来源定位、分类筛选、引用失效提示与重处理入口 | PDF/DOCX 解析是本方案建议扩展；异步批次和真实向量服务另接入 |
| 语料 | 样例/提示词/SQL/API、规则评测、JSONL 导出 | 统一显示关联智能体、测试集、当前发布版本、失败原因和改进记录；分离检索样例与评测样例 | NL2SQL/NL2API 生成、模型裁判与微调不等同于模板试运行 |
| 用户记忆 | 技能、结构化摘要、同用户任务接续 | 来源会话可追踪；支持用户明确选择是否带入场景/办件条件；记忆关闭、纠正和清除路径可见 | 真实语义压缩及长期记忆策略需模型集成 |
| 调用与反馈（既有扩展） | 节点追踪和反馈改进草稿 | `traceId` 串联应用、网关、AI、消息；显示失败、无结果、部分结果，避免只有成功样例 | 外部调用链与生产监控 |

### 6.2 地图、流程与智能助手的联动契约

场景可绑定已发布的智能体；运行页右侧提供“智能辅助”面板。业务办理页可绑定知识助手和指标助手，但助手只建议，不自动代替人工审批。

上下文建议：

```json
{
  "appId": "app_cropland",
  "appVersion": 1,
  "sceneId": "scene_cropland",
  "caseId": null,
  "regionCode": "150200",
  "timeRange": {"start": "2026-01-01", "end": "2026-12-31"},
  "visibleLayerIds": ["layer_cropland"],
  "selectedFeatureIds": [],
  "geometryRef": null,
  "crs": "EPSG:4490",
  "sessionId": null
}
```

以上为新字段建议。大范围几何使用有权限和有效期的 `geometryRef`，不把任意坐标串拼入提示词。传入的应用、图层和办件 ID 都是待服务端校验的引用，不是权限证明。

执行规则：

1. 服务端验证应用可用性、用户权限、引用对象存在性和版本。
2. 当前明确问题优先于已确认场景上下文，场景上下文优先于历史默认记忆；冲突条件在前台可见。
3. 返回资源、引用、指标和建议动作。地图定位/高亮只执行白名单动作，并再次验证图层、对象及坐标系。
4. 新建办件、提交申请、发起审批等有业务副作用的建议，由用户查看表单后明确提交，不能由助手静默触发。
5. 记录应用、智能体、知识、指标和上下文版本；数据撤权或应用下架后，历史引用按实时权限控制访问。

### 6.3 模型与真实服务的替换方式

建议设置 `SearchProvider`、`LLMProvider`、`EmbeddingProvider`、`SummaryProvider`、`ResourceApprovalAdapter` 接口。保留当前本地实现作为无密钥演示和回归基线；生产适配器独立配置并记录实际调用状态。

模型接入后仍执行现有资源权限、SQL 只读和参数校验；模型输出不决定权限。检索证据不足时返回无结果或待补充条件，不用固定答案覆盖异常。文档内容、用户问题和工具结果按数据处理，不接受其中要求执行管理命令的指令。

## 7. 数据模型、版本与迁移

### 7.1 新增逻辑对象

| `widget_groups`、`widgets`、`widget_versions` | groupId、code、manifest、entry、status、version | 编码+版本唯一；关联分组不得删除 |
| `business_groups`、`business_systems`、`business_models` | systemId、formId、workflowId、ruleIds、timePolicyId | 事项明确绑定资源与版本 |
| `forms`、`workflow_definitions`、`workflow_versions` | schema、nodes、transitions、bindings、status、version | 已发布版本只读；部署/发布状态分开 |
| `projects`、`cases` | projectId、modelId、workflowVersion、formData、region、area、areaUnit、status | 项目与办件分开，面积口径明确 |
| `workflow_instances`、`workflow_tasks`、`task_actions` | caseId、nodeId、assigneeId、status、dueAt、rev、idempotencyKey | 动作不可改写；完成任务与生成下一任务同事务 |
| `delegations`、`business_assets` | owner、scope、validity；kind、code、value、schema、version | 业务资源可以共享存储设施，但不同 kind 使用独立校验 |
| `organizations`、`role_assignments`、`access_policies` | parentId、regionCode、orgId、subject、action、object、scope | 不允许组织循环；授权不得超出授予者范围 |
| `auth_clients`、`external_bindings`、`login_events` | appId、clientKey、secretRef、policy、syncVersion、result | 密钥仅服务端；演示登录与正式登录可区分 |
| `gateway_routes`、`gateway_upstreams`、`gateway_calls` | appId、target、policy、traceId、durationMs、statusCode | 统计源于实际示例或真实调用结果 |
| `event_outbox`、`subscriptions`、`channels`、`deliveries`、`notifications` | eventId、subscriptionId、attempt、nextRetryAt、status、recipientId | 去重约束；投递记录不等同于已读状态 |

公共字段：`createdAt/updatedAt/createdBy/updatedBy/rev`。版本化资产另有不可变 `version` 和发布快照。编辑修订号与发布版本号不能混用。

### 7.2 对现有对象的兼容处理

- 现有 `applications` 保留其资源申请意义，新 API 使用 `resourceRequests` 别名。既有申请、授权、会话 ID 不变。
- 元数据模板仍存于既有 `templates`；新场景模板只使用 `scene_templates`。
- 新应用目录通过 `targetType/targetId/targetVersion` 引用现有智能体，避免复制其配置和发布历史。
- 新增统一 `assetRef={kind,id,version}` 用于应用依赖、流程依据及调用追踪，禁止只按同名文本关联。
- 扩展现有知识来源字段和会话业务上下文，旧记录缺省值为未绑定；不批量覆盖用户已保存内容。
- 现有区域主要使用中文名称，新上下文建议使用 `regionCode`。新增区划字典及名称/编码映射，兼容旧数据；无法映射的记录标记待核对，不默认转成“全区”。

### 7.3 存储实施顺序

当前状态保存在 SQLite 一行 JSON 中，适合小型原型，但场景版本、流程任务和消息队列不宜继续无限塞入同一对象。

1. 引入仓储接口封装现有 `state` 读取，业务函数不直接操作数据库连接。
2. 新增 `schema_migrations` 和应用/流程/消息领域表；原智能中心状态暂留旧表，避免一次性重写。
3. 同一个业务操作跨旧状态和新表时，使用同一 SQLite 连接与事务；outbox 写入也在该事务内。
4. 索引构建、模型调用、文件解析和消息推送先创建任务，再于事务外执行，最后用版本检查提交结果，不持有全局锁等待网络。
5. 迁移必须幂等；升级前备份，检查原资源、草稿、发布快照、申请、授权、会话与反馈的数量和关键字段。
6. 数据库回退与代码回退成对执行。升级后新增业务数据先导出保留，不直接用旧备份覆盖造成丢失；回退方案在隔离副本上演练。

保留 `GET /api/bootstrap`、`POST /api/action` 和 `POST /api/v1/agents/invoke`。新增页面通过新的领域 API 获取分页数据，避免一次 bootstrap 返回全部办件、消息和版本配置。

变更命令示例：

```json
{

  "expectedRev": 3,
  "idempotencyKey": "client-generated-unique-key",
```
