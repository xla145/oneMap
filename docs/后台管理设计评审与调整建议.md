# 一张图后台管理设计评审与调整建议

> 日期：2026-09-16。依据：[全局需求分析与后台设计基线](../img/all/一张图全局需求分析与后台设计基线.md)、当前 `prototype/` 实现及本地运行页面。本文为设计评审，不改变已批准范围；调整方案均为建议。

> 实施进展：本评审记录调整前的问题；2026-09-16 已完成首轮代码调整，已实现项、兼容规则、测试与剩余范围见[后台管理首轮调整说明](后台管理首轮调整说明.md)。

## 1. 评审结论与边界

当前后台已经具备可复用的应用、流程、智能资产、门户运营和公共支撑功能，但对象归属与生命周期仍沿用早期演示结构。继续直接增加菜单，容易形成多个中心重复登记同一对象、审批结果与实际访问规则不一致的问题。应先调整共享对象、授权模型和模块职责，再展开完整原型。

本次核对实际生效的菜单、页面渲染及后端逻辑，并用独立临时数据库启动原型，查看资源编辑和质量检查页面。另用纯内存输入验证资源授权判定，没有修改现有业务数据库和应用代码。不是生产系统安全审计，也没有重新验收所有功能。

以下区分三类：**现有设计问题**、**尚未覆盖的需求**、**基线文档需补充的设计约束**。未建设功能不直接判定为现有功能故障。文中的“优先调整”是设计依赖顺序，不代表建设合同的优先级。

## 2. 优先调整的问题

### 2.1 资源上的“已授权”与用户授权混用

**性质：现有设计问题；优先调整。**

资源编辑直接提供“使用权限：可申请 / 已授权”。后端遇到资源自身 `access=已授权`，即允许符合可见范围的用户使用，不要求存在该用户的授权记录。

证据：[授权判定](../prototype/backend/capabilities.py#L25)、[申请及审批](../prototype/server.py#L402)、[资源编辑器](../prototype/app.js#L912)。内存验证：同一普通业务用户、同一资源、授权清单为空，资源为“可申请”时结果为 False，改为“已授权”后为 True。

这不是向所有人无条件开放，部门、区域及可见性仍然约束访问；问题是管理员可能把“给某个人授权”误操作成“对可见人群开放”。即使原意就是开放使用，也不应使用“已授权”这个标签。

建议分开设计：

| 对象 | 配置或展示内容 | 维护位置 |
| --- | --- | --- |
| 资源共享策略 | 开放使用、申请使用、限制使用 | 资源共享配置 |
| 对象可见范围 | 哪些主体可以发现资源 | 目录与渠道配置 |
| 用户或应用授权 | 授权主体、资源、操作、范围、期限、状态、来源申请 | 授权台账 |
| 当前用户权限 | 未申请、审批中、已获授权、已过期等计算结果 | 前台资源详情 |

验收场景：只授权甲使用后，乙仍需申请；资源改为开放使用需明确展示影响范围；撤销甲的授权应影响后续调用。

### 2.2 审批通过与授权交付没有独立的管理闭环

**性质：已有闭环需要扩展；优先调整。**

当前已经实现逐资源审批、部分通过、补充说明、撤回、历史记录和消息通知，应保留。审批通过时写入的授权仅包含用户、资源、截止日期，缺少独立授权编号、来源申请明细、启停/撤销状态、操作和数据范围等信息。[证据](../prototype/server.py#L402)

后果是“谁批准、批准了什么范围、现在还能否用、具体交付是否完成”不能完整地通过授权对象追溯。后续接入接口、下载、订阅等不同共享方式时，也难以表达审批通过但交付失败。

建议在既有审批页上扩展申请和核准明细，增加授权台账及交付记录。核准范围应明确，不能默认审批人员只能全量接受申请期限与范围。不同交付方式按实际需求启用；即时本地授权可以自动生成交付成功记录，不必增加无意义的人工步骤。

最小关联：`申请 → 申请明细 → 审批结果 → 授权记录 → 交付/调用结果`。授权有效性、服务可用性与审批状态分别展示。

### 2.3 平台资源、身份和知识被收进“门户管理”

**性质：现有信息架构问题；优先调整。**

当前“门户管理”下包含资源与元数据、资源审批、质量检查、组织身份及登录接入；“系统管理”主要是监测、审计和安全；“公共支撑”又放网关、消息和配置。[菜单证据](../prototype/app.js#L249)

门户是共享能力的使用和展示渠道，这种归属使全平台对象看起来像门户私有配置，也让管理员难以按工作职责找到入口。AI 知识被放在资讯管理中，与智能中心的工作内容脱节。

建议：门户仅管理首页、栏目、文章展示、附件、专题、办事指南、公众反馈、对外注册审核和门户统计；共享资源、工具、知识、平台身份各有明确主入口。跨模块使用详情链接或引用选择器，不复制主数据。

调整菜单时保留原路由并提供过渡入口，避免把信息架构调整扩大为全部功能重写。

### 2.4 工具有两套登记和权限入口，缺少统一对象关联

**性质：现有对象模型问题；优先调整。**

一套是资源目录中的“工具服务”，参与资源申请与授权；另一套是门户的“能力服务管理”，维护执行引擎、入口地址、门户角色、版本和上下架。门户工具表单中没有关联资源对象的字段。[资源编辑](../prototype/app.js#L912)、[门户工具登记](../prototype/frontend/portal-admin.js#L48)、[工具种子与模型](../prototype/backend/portal_management.py#L30)

两套工具当前不一定是同一个业务实例，因此不能直接断言存在重复数据；但同一工具需要同时进入内部资源中心和外部工具中心时，缺少明确关联机制，会出现分别维护名称、版本、权限与调用统计的问题。

建议建立稳定的工具主标识，关联执行定义、版本、内部目录项、对外上架项及接口密钥范围。内部与外部可以有不同授权政策，但必须能够追溯到同一工具版本。保留现有门户工具的注册、发布、停用和密钥能力。

### 2.5 资讯发布和 AI 知识处理共用内容状态

**性质：现有生命周期问题；优先调整。**

资讯种子直接写入 `knowledge`，执行知识切片处理后发布；资讯展示和 AI 知识检索都使用该类对象。没有清晰区分文章对外发布、知识纳入检索、政策作为业务依据这几种用途。[资讯初始化](../prototype/backend/news_content.py#L23)、[知识检索](../prototype/backend/capabilities.py#L76)、[资讯展示](../prototype/frontend/news.js#L18)

AI 检索仍有可见性、绑定范围和相似度筛选，不能说每篇资讯都会进入每次回答。但内容生命周期共用后，很难独立表达“文章仍公开可读，但不再作为知识依据”或“知识已更新，门户仍使用旧发布版”。

建议共享原始文档和附件，分别维护文章发布版本、知识处理与索引版本、业务依据有效版本。知识对象显式引用原文版本，提供纳入/退出知识库操作。不要把资讯编辑人员的基本操作与切片、图谱配置放在同一必经流程中。

## 3. 能力缺口与页面设计问题

### 3.1 元数据完整性检查不能代表数据质量合格

**性质：现有结果表达问题，同时存在较大的需求覆盖缺口。**

当前“资源语义与质量”检查来源、坐标系、更新频次、业务同义词和字段说明，满足条件即显示“合格”。它没有据此检测业务记录、空间几何、标准符合性或入库结果。[计算逻辑](../prototype/backend/platform_domain.py#L123)、[质量页面](../prototype/frontend/platform.js#L101)

建议立即把结果名称改为“元数据完整性通过 / 待补充”，保留现有检查作为发布前校验的一部分。数据质量另建规则/模型、任务、报告、问题整改与复检链路。

基线的 D01-D12 涵盖归集、登记、质检、整改、标准、建库和技术发布，当前没有形成对应的完整管理链路。这属于运营中心的重要建设缺口，不能通过重命名“资源语义与质量”认定已覆盖。

建议先用一批数据串起：`归集批次 → 检查任务 → 问题报告 → 整改 → 复检 → 登记/入库 → 服务发布 → 共享目录`。对已登记存量资源支持按适用流程接入，避免强制重新归集。

### 3.2 资源编辑弹窗承担过多职责

**性质：已验证的交互问题。**

同一弹窗包含基础目录信息、技术元数据、字段级 AI 配置、访问部门、关系规则、服务地址以及 SQL 表名和 CSV 示例数据。运行页面首屏仅能显示部分基础字段，完整字段需要在弹窗中持续滚动。[编辑器](../prototype/app.js#L912)

其中“类型|目标资源标识|本字段|目标字段”和逗号分隔部门等输入要求操作者理解内部结构，也不利于选择校验。

建议改为资源详情工作区：基本信息、技术元数据、AI 语义、关联关系、共享与发布、授权记录、运行与变更。新建时按库表/服务/工具/文档类型展示适用字段；关系使用对象选择及字段映射，部门使用组织选择。演示 SQL/CSV 放入明确的高级或演示配置入口。

保留已有草稿、发布和历史版本机制。不同角色只编辑其职责范围的配置；工作区分页不意味着每个页签再建一个左侧菜单。

### 3.3 菜单展示与可管理权限不一致

**性质：现有角色体验问题。**

导航仅对“资源审批人员”做专门过滤，其他后台角色得到完整菜单；具体页面随后按应用、流程、系统及身份管理权限显示“暂无管理权限”。部分门户后台仅允许平台管理员。[导航过滤](../prototype/app.js#L290)、[页面权限判定](../prototype/frontend/platform.js#L278)、[门户权限判定](../prototype/frontend/portal-admin.js#L24)

这会让专职管理员看到大量不能操作的入口。页面及后端已有权限校验，不能把此问题描述为“没有权限控制”。

建议由同一套能力声明生成菜单、页面动作与服务端校验依据；组织、业务范围和角色职责分别建模。对无权页面默认隐藏；确需展示可申请能力时，提供明确说明和申请入口。

### 3.4 总览没有围绕各岗位的待办工作组织

**性质：现有工作台设计需要扩展。**

实际生效的总览展示已上架应用、在办事项、智能体和待处理投递，内容偏应用与智能资产。资源审核、注册审核、治理异常和运行告警没有形成跨模块待办入口。[实际总览](../prototype/frontend/platform.js#L59)

建议保留现有概览，根据角色配置待办、异常、近期变更和常用入口。资源审批人员关注待审申请及超时；治理人员关注失败任务与整改；运维人员关注告警和失败投递。卡片直接跳到已筛选列表，明确统计范围和更新时间。

## 4. 基线文档也应补充约束

原文档已将菜单、字段、状态机和优先级标为建议，并明确需要结合实际实现评估。它适合作为需求追踪底稿，还不能直接作为最终后台 PRD。

| 需补充内容 | 当前不足 | 建议处理 |
| --- | --- | --- |
| 存量功能映射 | 54 个功能与页面组容易被当成 54 个菜单或全新页面 | 保留编号用于追踪，标注每组为复用、调整、新增或对接；再决定菜单、页签、详情和操作 |
| 统一对象关系 | 概念定义尚未落实到当前对象 | 明确资产、服务、目录项、工具、渠道发布、申请、授权、交付之间的标识和关系 |
| 独立状态和版本 | 状态机建议还需结合实现落地 | 分开草稿/发布版本、渠道上架、审批、授权、交付、知识索引状态，定义联动规则 |
| 内外发布渠道 | 当前通用可见范围不足以表达所有渠道要求 | 补充内部共享/对外公开的发布范围、审核及版本；详细部署路径仍待对接确认 |
| 管理权限范围 | 文档建议平台管理权不等同全部数据读取权，而原型管理员有更宽访问能力 | 明确演示特权与目标管理角色的差异；后续补充管理、审批、使用、审计权限矩阵 |
| 外部系统边界 | 需求清单不等于所有能力本地重建 | 对既有身份、工作流、交换、质检、GIS 服务等逐项确定复用/对接/自建，未确认项保留待定 |
| 异常与影响分析 | 主流程之外仍需明确业务规则 | 补充资源停用后的授权与依赖影响、工具新版本发布、知识退出索引、交付失败重试和历史追溯 |

不要仅依据菜单数量计算需求完成率。要分别统计页面覆盖、流程可执行、权限有效、结果落地和真实系统接入情况。

## 6. 建议的设计推进顺序

1. **先定共享对象与状态。** 明确资源/工具主标识、共享策略、授权、渠道发布和知识版本关系；形成一张对象关系图及状态转换表。
2. **再定职责与菜单。** 用平台管理员、资源审批、治理、工具运营、内容编辑、应用管理、AI 运营、运维等岗位验证入口；最终岗位是否拆分按实际组织确定。
3. **改造最关键的原型链路。** 优先完成资源详情工作区、申请明细、授权台账和交付结果，再补工具关联及内容/知识双生命周期。
4. **补运营中心主链路。** 选择一批数据展示归集、质检、整改、入库、服务发布与目录引用，不能只补列表。
5. **扩展全局工作台和异常场景。** 让待办、失败、过期、停用及版本变更可被对应角色发现和处理。

首轮原型验收至少覆盖：甲乙授权隔离、授权撤销、审批通过但交付失败、内部可用但未对外上架、同一工具两渠道版本关联、文章公开但退出 AI 检索、质检整改复检、专职管理员只看到职责入口。

现有应用/流程、工具发布、密钥管理、门户附件、审计监控和智能资产能力均有复用价值。此次调整的重点是让这些能力共享明确的对象关系，并形成一致的管理流程。
